29  Customizing and building containers

Learning Objectives

  1. Write a container file (e.g., Dockerfile) that can be used to reproducibly build a container image that would contain the needed software and environment dependencies of your data science project
  2. Use manual and automated tools (e.g., Docker, GitHub Actions) to build and share container images
  3. List good container base images for data science projects

Download the images before you start

The examples in this chapter build on rocker/r-ver:4.6.2, which takes more than a gigabyte of disk space. Start Docker first (on macOS and Windows, open Docker Desktop), then download (pull) it before you start:

Terminal
docker pull rocker/r-ver:4.6.2

29.1 Building container images from Dockerfile’s

  • A Dockerfile is a plain-text file that contains commands primarily about what software to install in the Docker image. This is the more trusted and transparent way to build Docker images.

  • Once we have created a Dockerfile, we can build it into a Docker image.

  • Docker images are built in layers, and as such, Dockerfiles always start by specifying a base Docker image that the new image is to be built on top of.

  • Docker containers are all Linux containers and thus use Linux commands to install software. However, there are different flavors of Linux (e.g., Ubuntu, Debian, CentOS, Red Hat), and thus you need to use the right Linux install commands to match your flavor of container. For this course, we will focus on Ubuntu- or Debian-based images (and that means if we need to install software outside of R and Python packages, we will use apt-get as our installation program). However, most of what we’ll be doing for installation is R, Python, and their packages. For those, an image uses the same tools as your laptop, uv for Python and renv for R, which the next chapters put into an image.

Noteapt or apt-get?

Ubuntu has two commands for its package manager. apt is designed for people typing at a terminal, and its behavior may change between versions. apt-get is the older command, which keeps working the same way, so Ubuntu’s apt manual page recommends apt-get for scripts. The RUN lines in a Dockerfile are a script, so this book uses apt-get in them. apt even prints a warning when a script runs it:

Output
WARNING: apt does not have a stable CLI interface. Use with caution in scripts.

At a container’s prompt either command works, but using apt-get there too means you can copy the command that worked straight into the Dockerfile.

29.1.1 Workflow for building a Dockerfile

It can take a LOOOOOOOONNNG time to troubleshoot the building of Docker images. Thus, to speed things up and be more efficient, we suggest the workflow below:

  1. Choose a base image to build off (from https://hub.docker.com/).

  2. Create a Dockerfile named Dockerfile and save it in an appropriate project repository. Open that file and type FROM <BASE_IMAGE> on the first line. Add any files that need to be accessed at build time via the COPY command.

  3. In a terminal, type docker run --rm -it <BASE_IMAGE> bash and interactively try the install commands you think will work. Edit and try again until the install command works. The bash at the end starts a Bash shell in place of the image’s default command.

  4. Write working install commands in the Dockerfile, preceding them with RUN, and save the Dockerfile.

  5. After adding every 2–3 commands to your Dockerfile, try building the Docker image via docker build --tag <TEMP_IMAGE_NAME> <PATH_TO_DOCKERFILE_DIRECTORY>.

  6. Once the entire Dockerfile works from beginning to end on your laptop, then you can finally move to building remotely (e.g., creating a trusted build on GitHub Actions).

29.1.2 Build your first image

Let’s follow the workflow to build a small image with R and the R package cowsay, which draws an animal saying whatever you give it.

For step 1, the base image is rocker/r-ver:4.6.2, Ubuntu Linux with R 4.6.2 installed. For step 2, make a folder for the project and move into it:

Terminal
mkdir hello-cowsay
cd hello-cowsay

In a text editor, create a file in that folder named Dockerfile, with no file extension, that has one line:

FROM rocker/r-ver:4.6.2

For step 3, start a container from the base image with a Bash shell:

Terminal
docker run --rm -it rocker/r-ver:4.6.2 bash

Inside R, you would install the package with install.packages("cowsay"). At the container’s Bash prompt, Rscript -e runs a line of R code instead, which is the form a RUN line needs:

For step 4, write the commands that worked into the Dockerfile:

FROM rocker/r-ver:4.6.2

RUN runs the install while the image is built. It is the same command you typed at the container’s Bash prompt, which is one reason this book works at the command line (see Introduction to the Bash Shell). CMD sets the command a container from this image runs when it starts. It replaces the base image’s own CMD ["R"] (see Introduction to containerization), so a container runs our line of R code instead of starting R.

29.1.3 Layer caching

Docker saves each step’s result as a layer, and reuses a layer when nothing in its step, or in the steps above it, has changed. To see this, change only the message on the CMD line of the Dockerfile:

CMD ["Rscript", "-e", "cowsay::say('Moo! Only my message changed.')"]

Then build again:

docker build --tag hello-cowsay .

This is why a Dockerfile puts the steps that change least often, such as installing software, near the top, and the steps that change most often near the bottom. A change to one step rebuilds that step and every step below it.

29.1.4 Guidelines for RUN commands

Each RUN command creates a new layer in the Docker image. Each layer in a Docker image takes more disk space. As a consequence, we want to minimize the number of layers where reasonably possible. How can we do this?

Install everything that can be installed by a tool (e.g., apt-get, or install.packages() in R) at once (i.e., when installing 5 programs via apt-get, do not call apt-get five times; instead do: apt-get install tool1 tool2 tool3 tool4 tool5, and in R, install.packages(c("pkg1", "pkg2"))). However, doing this can lead to long lines. In response, we can break a single command across lines in the shell by using the \ character. For example, to reduce the long line below, which uses apt-get to install the programs Git, Tiny Nano, Less, and wget:

Terminal
apt-get install --yes git nano-tiny less wget

We can use \ after each program to break the long command across lines and make the command more readable (especially if there were even more programs to install). Similarly, we indent the lines after \ to increase readability:

Terminal
apt-get install --yes \
    git \
    nano-tiny \
    less \
    wget

We can also group together related commands that depend upon each other. When doing this, we need to be careful, though, as sometimes we don’t want to run a command if the command that was run immediately before it failed. We can specify this in the shell using &&. For example, if we want to not run apt-get installation commands if apt-get update failed, we can write:

Terminal
apt-get update && \
    apt-get install --yes git

29.2 Dockerfile command summary

The most common Dockerfile commands I use:

Command Description
FROM States which base image the new Docker image should be built on top of
RUN Specifies that a command should be run in a shell
ENV Sets environment variables
EXPOSE Specifies the port the container should listen to at runtime
COPY or ADD Adds files (or URLs in the case of ADD) to a container’s filesystem
CMD Sets the default command a container runs when it starts; a command after the image name in docker run replaces it
ENTRYPOINT Sets a command that always runs when a container starts; anything after the image name in docker run is passed to it as arguments
WORKDIR Sets the working directory for any RUN, CMD, ENTRYPOINT, COPY and ADD instructions that follow it in the Dockerfile

And more here in the Dockerfile reference.

29.2.1 CMD or ENTRYPOINT?

Both set what a container runs when it starts. They differ in what docker run can replace. A command after the image name in docker run replaces CMD. For example, this runs R --version in the hello-cowsay image in place of its cowsay message (head -1 keeps the first line):

Terminal
docker run --rm hello-cowsay R --version | head -1
Output
R version 4.6.2 (2026-10-29) -- "Diversified Portfolio"

ENTRYPOINT is not replaced this way. Anything after the image name is passed to it as arguments, and replaces only CMD. With both, ENTRYPOINT holds the part that always runs, and CMD holds the default arguments. For example, this Dockerfile, in a folder of its own, always runs Rscript -e, with cowsay R code as the default:

FROM rocker/r-ver:4.6.2

RUN Rscript -e "install.packages('cowsay')"

ENTRYPOINT ["Rscript", "-e"]
CMD ["cowsay::say('Hello from my first image!')"]
Terminal
docker build --tag cowsay-entrypoint .
docker run --rm cowsay-entrypoint
Output
 ____________________________ 
< Hello from my first image! >
 ---------------------------- 
      \
       \

        ^__^ 
        (oo)\ ________ 
        (__)\         )\ /\ 
             ||------w|
             ||      ||

Passing different R code replaces the default, but still runs it with Rscript -e:

Terminal
docker run --rm cowsay-entrypoint "cowsay::say('Only the R code changed.')"
Output
 __________________________ 
< Only the R code changed. >
 -------------------------- 
      \
       \

        ^__^ 
        (oo)\ ________ 
        (__)\         )\ /\ 
             ||------w|
             ||      ||

The images in this book, rocker/r-ver among them, set only CMD, so that a command such as bash after the image name replaces it, as in step 3 of the workflow.

29.3 Choosing a base image for your Dockerfile

Source: https://themuslimtimes.info/2018/10/25/if-i-have-seen-further-it-is-by-standing-on-the-shoulders-of-giants/

29.3.1 Good base images to work from for R or Python projects!

Image Software installed
rocker/r-ver Ubuntu Linux and R; the base of this book’s R examples
rocker/rstudio R, RStudio
rocker/tidyverse R, R packages (including the tidyverse), RStudio, Make; ARM-based computers need tag 4.5.1 or later
ubuntu Ubuntu Linux only; add uv to install Python and its packages
python Debian Linux and Python; the -slim tags leave out software most projects do not need
quay.io/jupyter/datascience-notebook JupyterLab, with libraries for data analysis from the Python, R and Julia communities
WarningUse rocker/tidyverse:4.5.1 or later

rocker/tidyverse images before 4.5.1 were built only for Intel and AMD computers (amd64). From 4.5.1 on, they are also built for ARM computers (arm64), such as Macs with Apple silicon. On an ARM computer, pulling an older tag fails:

Terminal
docker pull rocker/tidyverse:4.5.0
Output
Error response from daemon: no matching manifest for linux/arm64/v8 in the manifest list entries: no match for platform in manifest: not found

So use 4.5.1 as the minimum version. The rocker/tidyverse tags page lists each tag with the platforms it was built for (linux/amd64, linux/arm64), so you can check a tag before you use it.

29.4 Dockerfile FAQ

These questions come up when you start writing your own Dockerfile.

29.4.1 1. Where does the Dockerfile live?

The Dockerfile should live in the root directory of your project.

29.4.2 2. How do I make an image from a Dockerfile?

There are 2 ways to do this! I use the first when developing my Dockerfile (to test quickly that it works), and then the second when I want a build that others can check, made from the Dockerfile in the repository.

  1. Build a Docker image locally on your laptop

  2. Build a Docker image on GitHub Actions (see Building images for several platforms)

29.4.3 3. How do I build an image locally on my laptop?

From the directory that contains your Dockerfile (usually your project root):

Terminal
docker build --tag IMAGE_NAME:VERSION .
Note

--tag lets you name and version the Docker image. You can call this anything you want. The version number/name comes after the colon.

After I build, I then try to docker run ... to test the image locally. If I don’t like it, or it doesn’t work, I delete the image with docker rmi {IMAGE_NAME}, edit my Dockerfile, and try to build and run it again.
